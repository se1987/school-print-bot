# 技術選定理由（転職エージェント用アピールドラフト）

## プロジェクト概要

学校から配布される紙のプリント（行事予定・持ち物・下校時刻など）を、LINE で写真／PDF を送るだけで AI が自動解析し、子どもの学年に応じてパーソナライズされたリマインドを毎朝通知する個人開発のBot。「家庭の情報管理コストを削減する」という実需要から出発し、**運用コストゼロ・1人で保守可能**を制約条件として技術を選定した。

---

## 全体方針

| 観点 | 選定基準 |
| --- | --- |
| **コスト** | 月額無料枠で運用できること（LINE / Gemini / Railway すべて無料枠で完結） |
| **保守性** | 1人で運用するため、依存サービス・コンポーネントを最小化 |
| **拡張性** | 後から Google Calendar 連携など機能追加できる疎結合構造 |
| **学習価値** | 業務で活きる技術（FastAPI / LLM API / 非同期 I/O）を実プロダクトで習熟する |

---

## 各技術の選定理由

### Python 3.11 + FastAPI

- **非同期処理が必須**: LINE Webhook は3秒以内に応答する必要があり、Gemini API の解析（数秒かかる）を同期実行すると確実にタイムアウトする。`async/await` を第一級でサポートする FastAPI を採用し、Webhook 受信後すぐ 200 を返してバックグラウンドで AI 解析を走らせる構成にした。
- **Flask との比較**: Flask + Gunicorn + 非同期化ライブラリの組み合わせより、ASGI ネイティブの FastAPI のほうが構成が単純。型ヒント駆動の自動バリデーションも開発体験が良い。
- **Pythonにした理由**: AI/LLM 系ライブラリ（google-genai 等）のエコシステムが最も厚く、Gemini API 連携で詰まらないこと。Pillow による画像前処理も簡潔に書ける。

### Google Gemini 2.5 Flash（AI 解析）

- **マルチモーダルが標準対応**: 学校プリントは画像／PDF が混在するが、Gemini はファイル種別を意識せず単一APIで処理できる。OpenAI を選ぶと PDF をページ単位で画像化する前処理が必要になり実装コストが上がる。
- **構造化出力（JSON Schema）対応**: タスク名・期日・対象学年・下校時刻を `responseSchema` で型定義し、パース失敗を実質ゼロにできた。プロンプトで「JSONで返して」とお願いする方式と比べ運用が安定する。
- **コスト**: Flash モデルは無料枠で個人利用には十分。プリント1枚あたりのトークン消費を抑えるため、画像サイズの正規化と必要最小限のフィールド設計を行った。

### LINE Messaging API（line-bot-sdk v3）

- **ユーザー獲得コストがゼロ**: 想定ユーザー（保護者）の大半が既に LINE を日常利用しており、独自アプリを作る場合と比べてインストール障壁・通知許諾の壁を完全に回避できる。「**ユーザーが既にいる場所に届ける**」という UX 上の判断。
- **v3 SDK を選択**: 旧 v2 と異なり Pydantic ベースで型が明確、async コンテキストでの取り回しが良い。Webhook 署名検証も標準提供。

### SQLite（運用 DB）

- **データ規模で十分**: 1家庭あたり年間数百件のプリント／タスクで、PostgreSQL を立てる必然性がない。Railway のボリュームに置くだけでスキーマ運用が完結。
- **JSON カラムで柔軟性確保**: `target_grades`（対象学年配列）と `dismissal_times`（学年ごとの下校時刻マップ）は要素数が可変で、正規化すると JOIN コストが増える。SQLite の TEXT に JSON を格納し、アプリ側でパースする割り切りを採用。
- **将来の移行を阻害しない**: 抽象化レイヤを薄く保ったため、利用者が増えた段階で PostgreSQL への切り替えは数百行レベルで済む見積もり。

### APScheduler（リマインドのcron実行）

- **アプリ内完結**: Railway Cron や AWS EventBridge のような外部スケジューラを足すと「無料運用」「1コンテナで完結」という制約が崩れる。FastAPI の lifespan に組み込むことで、デプロイ＝スケジューラの起動になる。
- **JST × UTC のずれを吸収**: 「毎朝7時 JST に通知」を `cron(hour=22)` UTC で記述。タイムゾーン関連の不具合は、実環境（Railway は UTC）に合わせて記述するのが最も誤解が少ない。

### Railway（ホスティング）

- **比較検討の結果**: Heroku（無料枠終了）／Render（スリープあり）／Fly.io（クレカ必須）と比較し、**無料枠 + スリープなし + GitHub 連携の自動デプロイ + ボリューム永続化**を満たすのが Railway だった（`docs/HostingComparison.jsx` に比較記録）。
- **SQLite と相性が良い**: ファイルシステムが永続化されるため、軽量DB戦略がそのまま機能する。

### Docker / docker-compose

- **本番との同等環境をローカルで再現**: Railway も内部的にコンテナ化されるため、Dockerfile を本番と同じ前提で書けば「自分の環境では動いた」問題を回避できる。
- **SQLite の永続化テスト**: ローカルでもボリュームマウントして再起動時のデータ保持を検証。

### Pillow（画像前処理）

- LINE から取得する画像は端末ごとに解像度がばらつくため、Gemini への送信前に長辺基準でリサイズしてトークン消費を平準化する目的で導入。

## 設計上のこだわり

### 1. 「学年別下校時刻」の正規化

学校のプリントには「1〜4年は13:00、5年は13:30」のように**1つのイベントに学年依存の値**が混在する。これを子どもごとに正しく出し分けるため、

- Gemini のプロンプトで `dismissal_times: {"1-4年": "13:00", "5年": "13:30"}` の形に正規化させる
- `database.is_task_relevant_to_child` で範囲表記（`1〜4`／`1-4`／`1～4`）をすべてパースする

という二段構えにした。**ドメインの複雑さを LLM に丸投げせず、検証可能なロジックに落とし込む**ことを意識している。

### 2. 失敗が許される箇所と許されない箇所を分離

- LINE Webhook: 失敗するとメッセージが二重送信される → 必ず3秒以内に応答
- Gemini 解析: 失敗してもユーザーに「再送してください」と返せる → 非同期でリトライ
- Google Calendar 連携: 未設定でも他の機能を止めない → optional に切り出す

「**致命的な経路を細く、失敗してよい経路を太く**」というポリシーで、コンポーネント間の依存方向を整理した。

### 3. 段階的拡張を阻害しない構造

`gemini_client.py` / `database.py` / `scheduler.py` を疎結合にしているため、Google Calendar 連携を後から数百行で追加できた。最初から完璧を目指さず、**動く最小構成 → 検証 → 機能追加** のサイクルを回したことが、結果として保守可能なコードベースを生んだ。

---

## 技術選定を通じて得たこと

- **要件 → 制約 → 技術** の順で意思決定する習慣（「使いたい技術ありき」ではない）
- LLM をプロダクトに組み込む際の **構造化出力・トークン最適化・失敗時のリカバリ** の設計勘所
- 個人開発でも「無料運用」「1人保守」という現実の制約を満たすために、**過剰な技術選定を避ける**判断軸
- 仕様が曖昧な実世界データ（手書きや学校独自フォーマットのプリント）に対し、**LLM とルールベースを組み合わせて検証可能性を確保する**アプローチ
